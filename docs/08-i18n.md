# 08 — Internationalization (AR / FR / EN)

## Absolute rule enforced by the codebase

When a language is selected, **no interface string from another language may be
visible**. Arabic is the default and is RTL; French and English are LTR.

## One global language state

- `src/lib/i18n.ts` creates the single i18next instance:
  `SUPPORTED_LANGUAGES = ["ar","fr","en"]`, `DEFAULT_LANGUAGE = "ar"`,
  `fallbackLng: "ar"`, `load: "languageOnly"`, `defaultNS: "common"`,
  `ns: ["common","admin"]`, `LANG_STORAGE_KEY = "janat-sahara-lang"`.
- The browser language **detector is deliberately not used**: the server and the
  first client render must both start in Arabic or hydration mismatches (e.g. the
  logo `alt` text) occur. Helpers `readStoredLang()` / `storeLang()` handle
  persistence manually.
- `src/components/providers/LanguageProvider.tsx` is the only place that:
  1. applies the stored preference **after mount** (post-hydration `useEffect`),
  2. persists the active language,
  3. syncs `<html lang>` and `<html dir>` (`dirFor`, `isRtl`, `RTL_LANGUAGES = ["ar"]`).
- `src/components/common/LanguageSwitcher.tsx` is the only UI that changes language
  (`i18n.changeLanguage`). Never let a component keep its own language state.

`src/routes/__root.tsx` renders the shell with `lang="ar" dir="rtl"` and
`suppressHydrationWarning`; the provider corrects it on the client.

## Translation files

```
src/locales/{ar,fr,en}/common.json         → namespace "common" (public site + shared)
src/locales/{ar,fr,en}/adminShell.json     ┐
src/locales/{ar,fr,en}/adminOps.json       ├ merged into namespace "admin"
src/locales/{ar,fr,en}/adminContent.json   ┘
```

The three admin fragments are spread into one `admin` namespace in `i18n.ts`
(`{ ...arShell, ...arOps, ...arContent }`). Keep key prefixes distinct
(`shell.*`, `ops.*`, `content.*`) to avoid collisions.

SEO strings live under `seo.*` in `common.json` and are read inside route `head()`
with `i18n.t(...)`.

Audit tooling: `scripts/i18n-audit.mjs` detects hardcoded strings / missing keys.

## Two content layers — never mix them

| Layer | Where | Mechanism |
| --- | --- | --- |
| **System UI translations** | labels, buttons, validation, emails headers | i18next JSON files |
| **Agency content** | packages, articles, branches, stats, hero, contact info | localized DB columns: base column = Arabic, `_fr`, `_en` siblings |

`src/lib/localize.ts` is the engine:

- `langSuffix(lang)` → `"" | "_fr" | "_en"`.
- `localizeField(row, field, lang)` — returns the suffixed value, falling back to
  the base (Arabic) value.
- `localizeList(row, field, lang)` — same for JSON array columns
  (`included`, `excluded`, `timeline`, `required_documents`, `seo_keywords`).
- `useLocalized()` — hook wrapper bound to the active language;
  `pickLocalized` / `pickLocalizedList` for non-hook contexts.
- Formatting: `intlLocale`, `formatDate`, `formatLongDate`, `formatNumber`,
  `formatPrice`.
- Leak detection: `ARABIC_RE`, `hasArabic()`, and `pendingLabel(lang)` /
  `FR_PENDING = "Traduction en cours"` used when a translation is missing.

`KNOWN LIMITATION`: many seeded rows still have `NULL` `_en` (and some `_fr`)
columns, so English visitors see Arabic fallbacks or the "translation pending"
label for that content. This is data, not code — fill the columns in the admin.

## Admin language

The admin uses the same global i18next state and the `admin` namespace; the shell
exposes the language switcher. `KNOWN LIMITATION`: Smart Insight texts are generated
server-side in one language (see `06-admin-dashboard.md`).

## Adding a new translatable field

1. Migration: add `field`, `field_fr`, `field_en` to the table.
2. Read it through `localizeField` / `useLocalized`, never `row.field` directly in a
   public component.
3. Add the editor inputs (the admin field primitives already render the
   `(عربي) / (français) / (English)` suffix labels).
4. Add any new UI labels to all three locale files.
